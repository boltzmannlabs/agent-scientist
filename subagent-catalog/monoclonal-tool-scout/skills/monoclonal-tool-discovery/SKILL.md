# Tool discovery for the task

Cover every required operation, including evaluation, rather than collecting generators. Begin broad discovery alongside antigen research; finalize compatibility against the reviewed dossier and benchmark requirements. MAIN qualifies and executes scientific tools.

## User policy first

Read the actual request. Required/excluded tools, source order, local-only rules and download restrictions govern. If only one source is allowed, do not silently use another. Report unavailable/incompatible requested tools and allowed alternatives. Without a specified order, research **Boltzmann → ToolUniverse → open source**. This is discovery preference, not accuracy ranking. Cover meaningful alternatives and evaluation tools; do not stop at the first generator.

## Complete metadata, selective research

Inspect MAIN's captured schemas/deferred manifest and current installed canonical Boltzmann catalog, including unavailable entries, exact job names, modules and contracts. Use available granted read-only discovery for missing details or return a lookup request to MAIN. Absence of a bridge in your own context does not establish that MAIN lacks scientific tools.

Inspect existing ToolUniverse package specifications or an already configured discovery connection. Official listing/finder docs supply information, not proof of an authenticated executable service. No connector/credential change or installation follows from research permission. Search open-source primary repositories, releases, model cards, source and checkpoint publications. A repository is not a working local installation.

For each shortlisted tool record operation, input/format/context compatibility, output/adapter needs, version/check date, source/code/weights/service state, licenses, RAM/VRAM and runtime evidence, benchmark scope, independent validation, leakage and failure modes. Keep source-reported accuracy separate from readiness. Recency, confidence and model size do not establish superior accuracy.

For every selected operation include a same-objective alternative and the evidence needed to activate it. Check the exact task format, backbone conditioning, editable regions, required endpoint and resource feasibility; two tools in the same catalog category may solve different problems. When MAIN returns an actual failure, diagnose from its receipt/output and propose a supported replacement through the coordinator rather than excluding the requested objective. A terminal service success with missing chains or broken geometry does not upgrade readiness. Unknown accepted jobs retain their identity and are not resubmitted. Alternatives with different scoring definitions require benchmark review and new matched controls.

Cover annotation, generation/refinement, structure/context prediction, interface assessment, reference-based structural evaluation, sequence quality, developability, uncertainty and task-specific endpoints where applicable. Do not impose every metric as a universal gate.

Return requirement → tool → evidence/readiness → selection/replacement/incompatibility reason, including unfilled evaluation capabilities and exact lookup requests for MAIN. Give each consequential finding a stable ID and affected stages so MAIN can account for it. Use information-only, available-unverified, verified-for-inputs, setup-required, unavailable or incompatible. Only actual MAIN input qualification establishes execution state. Retain full catalog coverage in indexed artifacts rather than printing all entries in chat. Read the current tool-specific polling and submission contract; metadata or conflicting legacy skill text does not authorize a different execution mechanism.

Read [source guidance](references/source-guidance.md) for current primary-source lessons. You may inspect all supplied metadata, but must not submit jobs or execute candidate scientific tools to upgrade readiness.
